# Anthropic's official guidance for keeping Claude Code on track (as fetched 2026-10-24)

All quotes below were fetched from the live pages on 2026-10-24. Model names on the pages at fetch time: Claude Opus 5.5, Opus 5, Opus 4.8/4.7/4.6, Fable 5.1/5, Mythos 5.1/5, Sonnet 5.5/5/4.6, Haiku 5.5/4.5 ([Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)).

## Q1. Claude Code best practices: verification, TDD/tests, small steps, course-correcting, clearing context, plan mode

### Takeaway
The official guide's central claim is that context is the scarce resource and that Claude "stops when the work looks done", so you must give it a pass/fail check (tests, build, screenshot), make it show evidence, and gate the stop with /goal, a Stop hook, or a fresh-context verifier subagent. Plan mode is for exploring and planning before coding when the change is uncertain or spans several files. After two failed corrections, use /clear and write a better prompt.

### Cited Findings
- Core constraint: "Claude's context window fills up fast, and performance degrades as it fills... When the context window is getting full, Claude may start 'forgetting' earlier instructions or making more mistakes." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Verification: "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available, and you become the verification loop." The check is "a test suite, a build exit code, a linter, a script that diffs output against a fixture, or a browser screenshot compared against a design." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Before/after prompt examples: give example test cases and say "run the tests after implementing". For UI, "take a screenshot of the result and compare it to the original. list differences and fix them". Ask it to "address the root cause, don't suppress the error". — [Best practices](https://code.claude.com/docs/en/best-practices)
- Four levels of gating the stop: in one prompt; "Across a session: set the check as a `/goal` condition. A separate evaluator re-checks it after every turn"; "As a deterministic gate: a Stop hook runs your check as a script and blocks the turn from ending until it passes"; "By a second opinion: a verification subagent... has a fresh model try to refute the result, so the agent doing the work isn't the one grading it." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Evidence over assertion: "Have Claude show evidence rather than asserting success: the test output, the command it ran and what it returned, or a screenshot of the result." — [Best practices](https://code.claude.com/docs/en/best-practices)
- TDD-like patterns: "write a failing test that reproduces the issue, then fix it". Writer/tester split: "have one Claude write tests, then another write code to pass them." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Explore, Plan, Implement, Commit. Plan mode is entered with Shift+Tab or `claude --permission-mode plan`, and in it "Claude reads files and answers questions without making changes." Ctrl+G edits the plan. "Planning is most useful when you're uncertain about the approach, when the change modifies multiple files, or when you're unfamiliar with the code being modified. If you could describe the diff in one sentence, skip the plan." — [Best practices](https://code.claude.com/docs/en/best-practices)
- The plan written in plan mode is "Re-injected from disk" after compaction. — [Context window](https://code.claude.com/docs/en/context-window)
- Specs: "The most useful specs are self-contained: they name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step that proves the feature works." It also recommends interviewing the user with AskUserQuestion, writing SPEC.md, then "start a fresh session to execute it." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Course-correcting: Esc stops mid-action, Esc+Esc or /rewind restores, /clear resets. "If you've corrected Claude more than twice on the same issue in one session, the context is cluttered with failed approaches. Run `/clear` and start fresh with a more specific prompt... A clean session with a better prompt almost always outperforms a long session with accumulated corrections." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Failure patterns the guide names: "kitchen sink session", "correcting over and over", "over-specified CLAUDE.md", "trust-then-verify gap" ("If you can't verify it, don't ship it"), and "infinite exploration". — [Best practices](https://code.claude.com/docs/en/best-practices)
- Adversarial review: "Before treating a task as done, have a subagent review the diff in a fresh context and report gaps." Example: "review the rate limiter diff against PLAN.md. Check that every requirement is implemented, the listed edge cases have tests, and nothing outside the task's scope changed. Report gaps, not style preferences." Caveat: "A reviewer prompted to find gaps will usually report some, even when the work is sound... Chasing every finding leads to over-engineering... Tell the reviewer to flag only gaps that affect correctness or the stated requirements." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Fresh context for review: "A fresh context improves code review since Claude won't be biased toward code it just wrote." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Long-running harness research: failure modes were that an agent would "declare the job done" too early, tried to "one-shot the app", and had a "tendency to mark a feature as complete without proper testing". Fixes: a JSON feature list where the agent may only change a `passes` field ("It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality"), JSON chosen because the model is less likely to inappropriately change it than Markdown, a `claude-progress.txt` log, git commits, "work on only one feature at a time", and "use browser automation tools and do all testing as a human user would." (Nov 26, 2025) — [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

### Inferences
- The docs consistently treat instructions as soft and checks as hard. When something must happen, the recommended escalation is prompt, then /goal, then a Stop hook or verifier subagent.
- "Definition of done" in Anthropic's terms is a runnable check plus shown evidence, and for specs, an end-to-end verification step.

- I did not fetch the separate /goal page or the plan mode section of permission-modes. The details above come from the best-practices and context-window pages only.

## Q2. Prompting guidance for Opus 4.x/5.x: hard-coding tests, general solutions, hallucination, overengineering vs. full work, long-horizon state, honesty

### Takeaway
Anthropic publishes ready-to-paste prompts for each behavior: "write a high-quality, general-purpose solution... Do not hard-code values", "if any of the tests are incorrect, please inform me rather than working around them", `<investigate_before_answering>`, an anti-overengineering block, and, for Fable 5, a "ground progress claims" audit that "nearly eliminated fabricated status reports". Newer models (Opus 4.5+) overtrigger on aggressive language like "CRITICAL: You MUST". Opus 5 already self-verifies, so Anthropic says to remove blanket verification instructions and to constrain scope explicitly.

### Cited Findings
- Anti-hardcoding prompt: "Please write a high-quality, general-purpose solution using the standard tools available. Do not create helper scripts or workarounds to accomplish the task more efficiently. Implement a solution that works correctly for all valid inputs, not just the test cases. Do not hard-code values or create solutions that only work for specific test inputs. Instead, implement the actual logic that solves the problem generally... Tests are there to verify correctness, not to define the solution... If the task is unreasonable or infeasible, or if any of the tests are incorrect, please inform me rather than working around them." — [Prompting best practices, "Avoid focusing on passing tests and hardcoding"](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Hallucination in agentic coding: "<investigate_before_answering> Never speculate about code you have not opened. If the user references a specific file, you MUST read the file before answering. Make sure to investigate and read relevant files BEFORE answering questions about the codebase. Never make any claims about code before investigating unless you are certain of the correct answer - give grounded and hallucination-free answers." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- General anti-hallucination techniques: "Allow Claude to say 'I don't know'"; "ask Claude to extract word-for-word quotes first before performing its task" (for documents over 20k tokens); "Verify with citations... If it can't find a quote, it must retract the claim"; best-of-N; "External knowledge restriction". — [Reduce hallucinations](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-hallucinations)
- Honest progress reporting (Fable 5 page): "Before reporting progress, audit each claim against a tool result from this session. Only report work you can point to evidence for; if something is not yet verified, say so explicitly. Report outcomes faithfully: if tests fail, say so with the output; if a step was skipped, say that; when something is done and verified, state it plainly without hedging." Anthropic says this "nearly eliminated fabricated status reports even on tasks designed to elicit them." — [Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)
- Opus 5.5 capability note: its reports "say plainly what it did, what it found, and what it needs from you." It is "much less likely to state an incorrect figure or cite the wrong source." — [Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)
- Overengineering: "Claude Opus 4.5 and Claude Opus 4.6 have a tendency to overengineer by creating extra files, adding unnecessary abstractions, or building in flexibility that wasn't requested." The sample prompt: "Avoid over-engineering. Only make changes that are directly requested or clearly necessary... Don't add features, refactor code, or make 'improvements' beyond what was asked... Don't add error handling, fallbacks, or validation for scenarios that can't happen... The right amount of complexity is the minimum needed for the current task." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Scope in both directions (Opus 5): "Claude Opus 5 can also expand the scope of a task." The sample prompt: "Deliver what was asked, at the scope intended. Make routine judgment calls yourself, and check in only when different readings of the request would lead to materially different work. If the request seems mistaken or a better approach exists, say so in a sentence and continue with the task as asked rather than quietly narrowing, widening, or transforming it. Finish the whole task, and stop short of actions that are clearly beyond what was asked." — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- Opus 5 "completes full tasks rather than leaving stubs or placeholders, and it performs best when given the complete task specification up front and left to run." — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- Over-verification (Opus 5): "Claude Opus 5 verifies its own work without being told to. If your prompt contains explicit verification instructions ('include a final verification step for any non-trivial task,' 'use a subagent to verify'), remove them: instructions like these cause over-verification." On self-correction: "Avoid instructing re-checks it already performs ('double-check your answer,' 're-verify before responding')." — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- Literal compliance with limiting language (Opus 5): "If your review prompt says 'only report high-severity issues' or 'be conservative,' the model might follow that instruction literally and report less; ask it to report everything and filter in a separate pass instead." — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- Emphasis overtriggering: "Claude Opus 4.5 and Claude Opus 4.6 are also more responsive to the system prompt than previous models... these models might now overtrigger. The fix is to soften any aggressive language. Where you might have said 'CRITICAL: You MUST use this tool when...,' you can use more normal prompting such as 'Use this tool when...'". Also: "Tune anti-laziness prompting: If your prompts previously encouraged the model to be more thorough or use tools more aggressively, reduce that guidance." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Brief instructions suffice (Fable 5): "Instruction-following is improved enough that you can steer most behaviors with a brief instruction rather than enumerating each behavior by name." Old skills "are often too prescriptive... and can degrade output quality." — [Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)
- Give the reason: "Claude Fable 5 tends to perform better when the prompt states the intent behind a request." — [Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)
- Boundaries: "When the user is describing a problem, asking a question, or thinking out loud rather than requesting a change, the deliverable is your assessment. Report your findings and stop. Don't apply a fix until they ask for one." — [Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)
- Act vs. conservative: there is a `<default_to_action>` sample prompt and a `<do_not_act_before_instructions>` sample prompt: "When the user's intent is ambiguous, default to providing information, doing research, and providing recommendations rather than taking action." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Early stopping on unattended runs (Opus 5.5): "Treat a text-only end of turn as a report rather than as proof the task is done. Keep the task's parts in a checklist the model updates." It offers a long system-prompt addition naming four bad stop patterns, for example "a long summary of what was done that closes by announcing the next step and has no tool call." — [Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)
- Long-horizon state: "Have the model write tests in a structured format... (for example, `tests.json`)... Remind Claude of the importance of tests: 'It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality.'" Also "Use git for state tracking", progress.txt for freeform notes, and starting a fresh window with "Review progress.txt, tests.json, and the git logs." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Context awareness: "Your context window will be automatically compacted as it approaches its limit... do not stop tasks early due to token budget concerns. As you approach your token budget limit, save your current progress and state to memory before the context window refreshes." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Destructive shortcuts: "When encountering obstacles, do not use destructive actions as a shortcut. For example, don't bypass safety checks (e.g. --no-verify)." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- "Right altitude": avoid both "hardcoding complex, brittle logic in their prompts" and "vague, high-level guidance that fails to give the LLM concrete signals". (Sep 29, 2025) — [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

### Inferences
- A CLAUDE.md built on absolutes ("never", "inegociável", many MUSTs) runs against Anthropic's guidance for Opus 4.5 and later. That guidance favors short, specific, calm instructions with the reason attached, and emphasis on only one or two lines.
- Anthropic's own wording for "don't reduce scope" is the Opus 5 sentence about not "quietly narrowing, widening, or transforming" the request. It pairs that with "check in only when different readings... would lead to materially different work."

### Gaps
- I did not fetch the separate Opus 4.8 or Sonnet 5.5 pages. Their index entries mention "literal instruction following" and "verification on coding tasks".
- I found no official "definition of done" template beyond the spec guidance and the checks above.

## Q3. Compaction: what happens to CLAUDE.md and instructions, and how to re-inject rules

### Takeaway
After /compact or auto-compaction, the project-root CLAUDE.md, unscoped rules, auto memory, the plan-mode plan, skill descriptions, and invoked skill bodies (capped) are re-injected from disk. Instructions given only in conversation, hook-added context, nested CLAUDE.md files, and paths-scoped rules are summarized away until they reload. The documented fixes are to move the rule into the root CLAUDE.md, add "When compacting, always preserve..." to CLAUDE.md, use `/compact <focus>`, or add a SessionStart hook with the `compact` matcher.

### Cited Findings
- Survival table: "System prompt and output style | Both still apply"; "Project-root CLAUDE.md and unscoped rules | Re-injected from disk"; "Auto memory | Re-injected from disk"; "The plan Claude wrote in plan mode | Re-injected from disk"; "Rules with `paths:` frontmatter | ...reloads them on demand"; "Files Claude read or edited | Claude Code re-reads up to five, most recently modified first"; "Invoked skill bodies | Re-injected, capped at 5,000 tokens per skill and 25,000 tokens total"; "Context that hooks added earlier | Summarized with the rest of the conversation"; "SessionStart hooks that match the `compact` source | Claude Code runs them and adds their output to the compacted context". — [Context window](https://code.claude.com/docs/en/context-window)
- "If a rule must persist across compaction, drop the `paths:` frontmatter or move it to the project-root CLAUDE.md." Truncation of skill bodies "keeps the start of the file, so put the most important instructions near the top of `SKILL.md`." — [Context window](https://code.claude.com/docs/en/context-window)
- "Project-root CLAUDE.md survives compaction: after `/compact`, Claude re-reads it from disk and re-injects it into the session... If an instruction disappeared after compaction, it was given only in conversation... Add conversation-only instructions to CLAUDE.md to make them persist." — [Memory](https://code.claude.com/docs/en/memory)
- Hook recipe: "Use a `SessionStart` hook with a `compact` matcher to re-inject critical context after every compaction. Claude Code adds plain text your command writes to stdout to Claude's context." Example config: `"SessionStart": [{"matcher": "compact", "hooks": [{"type": "command", "command": "echo 'Reminder: use Bun, not npm...'"}]}]`. The `echo` can be replaced "with any command that produces dynamic output, like `git log --oneline -5`". — [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- PreCompact / PostCompact: matchers are `manual` and `auto`. PreCompact exit code 2 "Blocks compaction" and it supports `decision: "block"`. PostCompact has "No decision control". InstructionsLoaded has a `compact` load reason. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Compaction instructions in CLAUDE.md: "Customize compaction behavior in CLAUDE.md with instructions like 'When compacting, always preserve the full list of modified files and any test commands'". Also "run `/compact <instructions>`, like `/compact Focus on the API changes`". — [Best practices](https://code.claude.com/docs/en/best-practices)
- `/autocompact 500k` sets the threshold; `/rewind` can "Summarize from here" or "Summarize up to here". — [Context window](https://code.claude.com/docs/en/context-window)
- Subagents auto-compact too, with a per-agent `autoCompactWindow` frontmatter field. — [Subagents](https://code.claude.com/docs/en/sub-agents)
- API-level advice: consider starting a fresh window rather than compacting, because the models "are extremely effective at discovering state from the local filesystem." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)

### Inferences
- User corrections given in chat ("from now on, do X") are lost at compaction unless they are written to CLAUDE.md, a memory file, or a compact-matched SessionStart hook.

- I could not read the full PreCompact input schema (for example `custom_instructions`). The hooks reference page was truncated at 100k of 281k characters.

## Q4. CLAUDE.md writing and the memory hierarchy

### Takeaway
Keep each CLAUDE.md under about 200 lines and include only what Claude would get wrong without it. Bloat makes Claude ignore rules. Put "IMPORTANT" on a single line, not many. CLAUDE.md is delivered as a user message, it is advisory, and contradictory rules lead to arbitrary choices. Files load from managed, user, and project scopes plus every ancestor directory, all concatenated. Use hooks for anything that must always happen.

### Cited Findings
- "Keep it concise. For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it. Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" Its include/exclude table excludes "Self-evident practices like 'write clean code'", "Long explanations or tutorials", and "Anything Claude can figure out by reading code". — [Best practices](https://code.claude.com/docs/en/best-practices)
- "If Claude keeps doing something you don't want despite having a rule against it, the file is probably too long and the rule is getting lost." "If Claude keeps skipping one instruction, add emphasis such as 'IMPORTANT' to that line alone. If you emphasize many lines, none of them stands out." — [Best practices](https://code.claude.com/docs/en/best-practices)
- "Size: target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." Imports "don't reduce its context cost". — [Memory](https://code.claude.com/docs/en/memory)
- "Consistency: if two instructions contradict each other, Claude may pick one arbitrarily." `/doctor prompt-audit` finds "instructions written for older models... and files that contradict each other." — [Memory](https://code.claude.com/docs/en/memory)
- "CLAUDE.md content is delivered as a user message after the system prompt, not as part of the system prompt itself. Claude reads it and tries to follow it, but there's no guarantee of strict compliance, especially for vague or conflicting instructions." For system-prompt-level instructions, use `--append-system-prompt`. — [Memory](https://code.claude.com/docs/en/memory)
- "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook." "Make instructions more specific. 'Use 2-space indentation' works better than 'format code nicely.'" — [Memory](https://code.claude.com/docs/en/memory)
- Hierarchy: managed policy (`C:\Program Files\ClaudeCode\CLAUDE.md` on Windows), user `~/.claude/CLAUDE.md`, project `./CLAUDE.md` or `.claude/CLAUDE.md`, and local `./CLAUDE.local.md` (gitignored). "All discovered files are concatenated into context rather than overriding each other... instructions closer to where you launched Claude are read last." Subdirectory files load on demand. A user rule and a project rule that conflict: "Claude may follow either one". — [Memory](https://code.claude.com/docs/en/memory)
- `.claude/rules/*.md` with optional `paths:` globs. Unscoped rules load at launch "with the same priority as `.claude/CLAUDE.md`". — [Memory](https://code.claude.com/docs/en/memory)
- Auto memory: MEMORY.md, "The first 200 lines of `MEMORY.md`, or the first 25KB, whichever comes first, are loaded at the start of every conversation." It is not loaded into non-fork subagents. — [Memory](https://code.claude.com/docs/en/memory)
- Hooks vs CLAUDE.md: "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens." "If Claude already does something correctly without the instruction, delete it or convert it to a hook." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Multi-step procedures or rules relevant to part of the codebase belong in skills or path-scoped rules. — [Memory](https://code.claude.com/docs/en/memory)

### Inferences
- A two-level setup like the one in this repo (city/CLAUDE.md plus roadcraft/CLAUDE.md, both loaded and concatenated) needs both files kept consistent and short. Overlapping rules about reading, honesty, and research add length without adding signal.

## Q5. Subagents: configuration, what they receive, how results return, verifier patterns, delegating without losing requirements

### Takeaway
A subagent is a `.claude/agents/<name>.md` file with YAML frontmatter, where the body becomes its system prompt. A non-fork subagent gets its own prompt, the CLAUDE.md hierarchy (unless it opts out), and the task message Claude writes. It gets no conversation history, so any requirement left out of the delegation prompt is lost. Only the subagent's final summary returns to the parent. Forks inherit the full conversation. Recommended patterns are read-only reviewers (allowlist Read, Grep, Glob, Bash) and fresh-context verifiers that see only the diff and the criteria.

### Cited Findings
- Frontmatter fields: `name`, `description` (required), plus `tools`, `disallowedTools`, `model` (sonnet/opus/haiku/fable/full ID/inherit), `permissionMode` (default, acceptEdits, auto, dontAsk, bypassPermissions, plan, manual), `maxTurns`, `skills` ("full content is injected into context at startup"), `mcpServers`, `hooks`, `memory` (user/project/local), `background`, `isolation: worktree`, `effort`, `color`, `initialPrompt`, `omitClaudeMd`, `autoCompactWindow`. "Unrecognized fields are silently ignored." — [Subagents](https://code.claude.com/docs/en/sub-agents)
- What a non-fork subagent receives: its own system prompt plus environment details, but "does not get the Claude Code system prompt"; the "delegation prompt Claude writes"; "CLAUDE.md files: the full hierarchy, unless the subagent is Explore or Plan, or sets `omitClaudeMd: true`"; "Not included: your conversation history, previously invoked skills, or files already read." — [Subagents](https://code.claude.com/docs/en/sub-agents) (from a fetch summary of the page)
- Results: "When subagents complete, their results return to your main conversation." Only the summary returns. Agents can be resumed by ID with SendMessage and keep their history. — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Sub-agents return "a condensed, distilled summary of its work," often around 1,000–2,000 tokens. — [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Forks: "A fork is a subagent that inherits the entire conversation so far... Use a fork when any other subagent would need too much background to be useful." "A fork can't spawn further forks." — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Best practices: "Design focused subagents", "Write descriptions that single out one subagent", "Limit tool access", "Check into version control". The official code-reviewer example uses `tools: Read, Grep, Glob, Bash` with "limited tool access that excludes Edit and Write". The db-reader example backs its prompt with a PreToolUse hook: "the hook is a backstop." — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Output styles don't reach non-fork subagents: "Other subagents run their own system prompt, so styles don't change how they respond." — [Output styles](https://code.claude.com/docs/en/output-styles)
- Verifier with fresh context: "A reviewer running in a fresh subagent context sees only the diff and the criteria you give it, not the reasoning that produced the change." — [Best practices](https://code.claude.com/docs/en/best-practices)
- "Separate, fresh-context verifier subagents tend to outperform self-critique. For long-running tasks, instruct: `Establish a method for checking your own work at an interval of [X]... verifying your work with subagents against the specification.`" — [Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5); this is in tension with the Opus 5 advice "do not use subagents to verify or double-check your own work" in [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- Over-delegation: "Do not delegate work you can finish yourself in a handful of tool calls." Caps are `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` and `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`. — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- Hook-based verification: Stop and SubagentStop hooks with `type: "prompt"` return `"ok": false` and a `reason` that is "fed back to Claude so it keeps working". `type: "agent"` hooks "spawn a subagent that can read files, search code, and use other tools to verify conditions" (experimental). The example is "Verify that all unit tests pass." — [Hooks guide](https://code.claude.com/docs/en/hooks-guide)

### Inferences
- To delegate without losing requirements: put the full requirements (or a path to a spec or plan file) in the delegation prompt, because conversation history doesn't carry over. Put standing rules in CLAUDE.md, which subagents do load, or in the agent's own body or `skills`. Ask for evidence in the returned summary.
- The two sources disagree on whether to use subagents for verification. A reasonable reading: on Opus 5/5.5, avoid blanket "always verify with a subagent" instructions, and keep a targeted, fresh-context review against a written spec for long or unattended work.

### Gaps
- I did not see a documented field that lets the parent enforce a structured return format from a subagent. Return content depends on the subagent's prompt.

## Q6. Output styles, skills, and asking before reducing scope / definition of done

### Takeaway
Output styles change the system prompt for the main session. They are instructions, not guarantees, and custom styles drop Claude Code's built-in coding instructions unless `keep-coding-instructions: true` is set. Skills load on demand, so they suit procedures that are only sometimes relevant. On scope, the official guidance is to say so and continue as asked rather than "quietly narrowing", and to pause only for "a real scope change".

### Cited Findings
- "An output style gives Claude instructions to follow. It doesn't guarantee that something always happens or never happens." Built-in styles: Default, Proactive, Concise, Explanatory, Learning. — [Output styles](https://code.claude.com/docs/en/output-styles)
- "On the full system prompt, custom output styles leave out Claude Code's section of built-in software engineering instructions, such as how to scope changes, write comments, and verify work, unless `keep-coding-instructions` is set to `true`." Style files live in `~/.claude/output-styles` or `.claude/output-styles`. — [Output styles](https://code.claude.com/docs/en/output-styles)
- Feature selection table: output style for "Every response in a certain voice"; CLAUDE.md for project conventions; skill for "Instructions for one kind of task"; hook for "Something to happen every time without exception"; subagent for a focused helper; `--append-system-prompt` to append to the system prompt. — [Output styles](https://code.claude.com/docs/en/output-styles)
- Skills: "Claude loads them on demand without bloating every conversation." Use `disable-model-invocation: true` for side-effect workflows. — [Best practices](https://code.claude.com/docs/en/best-practices)
- Scope check-ins: "Pause for the user only when the work genuinely requires them: a destructive or irreversible action, a real scope change, or input that only they can provide." — [Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)
- "say so in a sentence and continue with the task as asked rather than quietly narrowing, widening, or transforming it. Finish the whole task" — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- A Stop prompt hook can check "if all tasks are complete. If not, respond with {\"ok\": false, \"reason\": \"what remains to be done\"}." — [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- Unattended runs: "If a turn ends with items still open and no blocker stated, send a short user message naming them... stop after two or three automatic continuations." — [Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)

### Inferences
- A "definition of done" is best made enforceable with a checklist file, a /goal condition, or a Stop prompt or agent hook, rather than with more CLAUDE.md prose.

- I did not fetch the full skills page (frontmatter such as `allowed-tools`, `context: fork`). The skills details here come only from the best-practices, context-window, and output-styles pages.
