# Claude Code hooks and permissions as enforcement tools (state as of Oct 2026)

Scope note: Everything below comes from pages fetched on 2026-10-24 from code.claude.com/docs (current docs; they cite versions up to v2.1.304) and from GitHub issue search results. The docs pages for hooks (281k chars) and managed settings were read in parts, so some sections were only partly fetched. Those are listed under Gaps.

## 1. Hook events and input JSON

### Takeaway
There are 33 hook events today, far more than the classic eight. Every event gets a common JSON envelope on stdin (session_id, transcript_path, cwd, permission_mode, hook_event_name, and so on) plus fields specific to the event. For enforcing honest completion, the events that matter are PreToolUse, PostToolUse, UserPromptSubmit, Stop, SubagentStop, TaskCompleted, PreCompact, SessionStart(compact) and ConfigChange.

### Cited Findings
- Full event list: `SessionStart`, `Setup`, `UserPromptSubmit`, `UserPromptExpansion`, `PreToolUse`, `PermissionRequest`, `PermissionDenied`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`, `Notification`, `MessageDisplay`, `SubagentStart`, `SubagentStop`, `TaskCreated`, `TaskCompleted`, `Stop`, `StopFailure`, `TeammateIdle`, `InstructionsLoaded`, `ConfigChange`, `CwdChanged`, `DirectoryAdded`, `FileChanged`, `WorktreeCreate`, `WorktreeRemove`, `PreCompact`, `PostCompact`, `PreModelSwitch`, `PostModelSwitch`, `Elicitation`, `ElicitationResult`, `SessionEnd`. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Five handler types: `command`, `http`, `mcp_tool`, `prompt`, `agent`. Agent hooks are marked experimental. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Common input fields: `session_id`, `prompt_id`, `transcript_path`, `cwd`, `scratchpad_dir`, `permission_mode` (`default|plan|acceptEdits|auto|dontAsk|bypassPermissions`), `effort` (object with `level`), `hook_event_name`, plus `agent_id`/`agent_type` when the hook fires inside a subagent or with `--agent`. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Example PreToolUse input: `{"session_id":"abc123","prompt_id":"...","transcript_path":".../transcript.jsonl","cwd":"/home/user/my-project","scratchpad_dir":"...","permission_mode":"default","hook_event_name":"PreToolUse","tool_name":"Bash","tool_input":{"command":"npm test","description":"Run test suite","timeout":120000,"run_in_background":false},"tool_use_id":"toolu_01ABC123..."}`. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- **Stop** input adds `stop_hook_active`, `last_assistant_message`, `background_tasks` and `session_crons`. `stop_hook_active` is "`true` when Claude Code is already continuing as a result of a stop hook". `last_assistant_message` holds the text of Claude's final response. Use it instead of reading `transcript_path`, because "the transcript file isn't guaranteed to include the final message at Stop time on all versions." — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Stop does not run on a user interrupt. API errors fire `StopFailure` instead, which has no decision control. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- **SubagentStop** input: `stop_hook_active`, `agent_id`, `agent_type`, `agent_transcript_path` (the subagent's own transcript in a nested `subagents/` folder), `last_assistant_message`, `background_tasks`, `session_crons`. `transcript_path` points to the main session's transcript. Some SubagentStop events come from internal agents (prompt suggestions, `/btw`), and for those `agent_type` may be empty. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- **SubagentStart**: the matcher is the agent type. The hook cannot block creation, but `additionalContext` is injected at the start of the subagent's conversation. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- **SessionStart** `source` is one of `startup|resume|clear|compact|fork`, and the matcher uses the same values. Optional fields: `model`, `agent_type`, `session_title`. On resume/fork there are cache fields such as `context_tokens` (v2.1.251+). Output can carry `additionalContext`, `initialUserMessage`, `sessionTitle`, `watchPaths`, `reloadSkills`. Plain stdout is also added to context. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- **PreCompact** matcher is `manual|auto`. Input adds `trigger` and `custom_instructions` (null for auto). **PostCompact** input adds `trigger` and `compact_summary`, and has no decision control. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- **TaskCompleted** fires when a task is marked completed through TaskUpdate, or when a teammate ends its turn with tasks still in progress. Input: `task_id`, `task_subject`, `task_description`, `teammate_name`. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- **ConfigChange** fires when a settings, managed policy or skill file changes. Matcher values: `user_settings|project_settings|local_settings|policy_settings|skills`. Input adds `source` and `file_path`. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- **FileChanged** uses a filesystem watcher, so it fires "no matter what changed the file: an Edit or Write tool call, a script Claude runs with Bash, or a process outside Claude Code entirely". Matcher entries are literal filenames in the working directory. It cannot block. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- **SessionEnd** `reason`: `clear|resume|logout|prompt_input_exit|other`. It cannot block, and the default budget is 1.5 s. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Matchers: `"*"`, `""` or omitted matches everything. A value made only of letters, digits, `_`, `-`, space, `,` and `|` is an exact list such as `Edit|Write`. Any other character makes it an unanchored JS regex. Matchers are case-sensitive. — [Hooks reference](https://code.claude.com/docs/en/hooks); [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- The handler-level `if` field uses permission-rule syntax (`"Bash(git *)"`, `"Edit(*.ts)"`) and only works on tool events. The docs call it "best-effort, so use the permission system for hard enforcement". — [Hooks reference](https://code.claude.com/docs/en/hooks)

### Inferences
- A completion gate should use `last_assistant_message` from Stop input to detect claims like "done", "tested" or "verified", and cross-check them against state on disk (test logs, screenshots, git diff) using paths from `cwd`.
- `FileChanged` is the only event that sees writes made through Bash or external scripts. It cannot block, but it can log or alert when a protected file is touched, for example a test file or a measurement script.

### Gaps
- I did not read the full per-event input schemas for UserPromptSubmit (the `prompt` field), PostToolUse (`tool_response`), PostToolUseFailure, PostToolBatch, Notification, InstructionsLoaded or Setup verbatim. Those sections were in the summarized part of the page.

## 2. Blocking semantics

### Takeaway
Exit code 2 (reason on stderr) and JSON `decision:"block"`/`permissionDecision:"deny"` are the two blocking channels. Exit 1 never blocks. Stop/SubagentStop blocks force Claude to continue, with `reason` as its next instruction. Loops are bounded by `stop_hook_active` plus a hard cap of 8 consecutive continuations. `onFailure:"block"` (v2.1.295+) closes the "a crashed policy hook lets everything through" hole on most events, but not on Stop.

### Cited Findings
- Exit 0: stdout is parsed as JSON only if it is a single JSON object. Otherwise it is plain text, which becomes context only on `UserPromptSubmit`, `UserPromptExpansion`, `SessionStart` and `PostModelSwitch`. Exit 2: blocking error, with stderr as the reason. Any other code: non-blocking error, and "Exit 1 is not a block." — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Per-event exit-2 table (verbatim rows): PreToolUse "Blocks the tool call". UserPromptSubmit "Blocks the prompt". Stop "Prevents Claude from stopping, continues the conversation". SubagentStop "Prevents the subagent from stopping". TaskCompleted "Prevents the task from being marked as completed". TaskCreated "Rolls back the task creation". ConfigChange "Blocks the configuration change from taking effect (except policy_settings)". PostToolUse "No — Shows stderr to Claude; the tool already ran". PostToolBatch "Yes — Stops the agentic loop before the next model call". PreCompact "Blocks compaction". SessionStart/SubagentStart/SessionEnd "No — Shows stderr to user only". PermissionRequest "No — exit 2 isn't honored". Notification "ignored". — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Universal JSON output fields: `continue` (default true; `false` "stops Claude entirely"), `stopReason` (shown to the user when continue=false), `suppressOutput` ("Accepted but has no effect"), `systemMessage` (a warning shown to the user), `terminalSequence`. The top-level `decision` can only be `"block"` with a `reason`. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- `hookSpecificOutput` requires `hookEventName`. PreToolUse takes `permissionDecision` (`allow|deny|ask|defer`) plus `permissionDecisionReason`, and `updatedInput`. PostToolUse takes `updatedToolOutput` and `additionalContext`. PermissionRequest takes `decision: {behavior: allow|deny, updatedInput}`. `additionalContext` is injected as a system reminder and capped at 10,000 characters per string. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Deny example: `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"Database writes are not allowed"}}`. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- A blocking exit code overrides JSON: "Even a `permissionDecision` of `"allow"` doesn't let the action through" when the hook exits 2. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Stop decision control: `decision:"block"` "prevents Claude from stopping", and `reason` is "Required when decision is block. Tells Claude why it should continue". Exit 2 routes stderr the same way. `hookSpecificOutput.additionalContext` also keeps the conversation going, but the transcript labels it "Stop hook feedback" rather than an error. Example: `{"decision":"block","reason":"Must be provided when Claude is blocked from stopping"}`. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Loop protection: "Claude Code applies an 8-consecutive-continuation cap: after stop hooks have continued the turn eight times in a row, Claude Code overrides the next block and ends the turn. The count of consecutive continuations resets each time Claude calls a tool. To raise the cap, set `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`." — [Hooks reference](https://code.claude.com/docs/en/hooks); the [Hooks guide](https://code.claude.com/docs/en/hooks-guide) recommends `if stop_hook_active == true; exit 0`.
- SubagentStop with `decision:"block"` keeps the subagent running, and the reason is delivered to it as its next instruction. To inject context into the parent, use PostToolUse on the `Agent` tool. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- TaskCompleted: exit 2 means "the task is not marked as completed and the stderr message is fed back to the model". `continue:false` is ignored when TaskUpdate triggered the event. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- UserPromptSubmit: `decision:"block"` stops the prompt. The reason is shown to the user and is not added to context. `additionalContext` is added. The default timeout is 30 s, and a timed-out hook's output is discarded while "the prompt still proceeds" unless `onFailure:"block"` is set. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- PostToolUse: `decision:"block"` adds `reason` next to the tool result, and "Claude still sees the original output". The tool already ran, so the hook cannot undo side effects. — [Hooks reference](https://code.claude.com/docs/en/hooks); [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- PreCompact: exit 2 or `decision:"block"` blocks compaction. Blocking an auto-compact that runs to recover from a context-limit error makes the request fail. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- ConfigChange can block settings changes (exit 2 or `decision:"block"`) except for `policy_settings`. A blocked change surfaces no message; Claude Code only writes a line to the debug log. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- `onFailure:"block"` (command/http, v2.1.295+): if the hook can't start, exits with a code other than 0 or 2, gets an HTTP error, times out, or returns invalid JSON, the result is treated like exit 2. "It has no effect on Stop, SubagentStop, TaskCompleted, TeammateIdle, or background (async/asyncRewake) command hooks." — [Hooks reference](https://code.claude.com/docs/en/hooks)
- A timed-out PreToolUse hook "doesn't block the tool call" by default (unless onFailure block). — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Async hooks (`async:true`) "can't block or control Claude's behavior". — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Misplaced fields (for example `permissionDecision` at the top level) are silently ignored. The debug log shows `Hook JSON output had unrecognized keys`. Shell-profile output printed before the JSON makes Claude Code treat it as plain text, which also fails silently. — [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- A PreToolUse `deny` from a hook holds in every mode, "even in bypassPermissions mode or with --dangerously-skip-permissions". PreToolUse fires before any permission-mode check. — [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- `/goal` is a built-in shortcut for a session-scoped prompt-based Stop hook. — [Hooks reference](https://code.claude.com/docs/en/hooks)

### Inferences
- A false-completion gate built as a Stop command hook can be defeated in two ways. After 8 consecutive blocks without a tool call, the stop is forced through, though each tool call resets the count. And if the script crashes, the turn simply ends, because onFailure does not apply to Stop. Write the Stop script defensively: catch internal errors and exit 2 with a message, rather than crashing.
- Because a tool call resets the cap, an agent that runs one trivial tool per iteration can keep a Stop gate in an unbounded loop. The gate should therefore check real evidence, not just text.
- Use TaskCompleted with exit 2 to stop tasks from being marked complete without evidence.

### Gaps
- The verbatim PreToolUse decision-control section (what `defer` and `ask` do exactly, and how disagreeing hooks combine) fell in the summarized portion. The only stated precedence rule is the PreModelSwitch one, `deny > ask > allow`. The combination rule for PreToolUse is not confirmed.

## 3. Prompt-based and agent-based hooks

### Takeaway
`type:"prompt"` sends a single LLM call to the background model and expects `{ok, reason, impossible}` back. `type:"agent"` spawns a subagent with Read/Grep/Glob (and other tools) for up to 50 turns. Both are supported on Stop, SubagentStop, PreToolUse, PostToolUse, TaskCompleted and some other events, but not on SessionStart, PreCompact or ConfigChange. Agent hooks are experimental. On Stop, the `impossible` field lets the judge model release the stop, which an adversarial agent could influence.

### Cited Findings
- Events supporting all five types: `PermissionDenied`, `PostToolBatch`, `PostToolUse`, `PostToolUseFailure`, `PreToolUse`, `Stop`, `SubagentStop`, `TaskCompleted`, `TaskCreated`, `TeammateIdle`, `UserPromptExpansion`, `UserPromptSubmit`. `PermissionRequest` supports prompt but not agent. `SessionStart` and `Setup` support only command and mcp_tool. ConfigChange, PreCompact, PostCompact, SubagentStart, SessionEnd and others support no prompt or agent hooks. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- How prompt hooks work: they "Send the hook input and your prompt to a Claude model, by default the one Claude Code uses for background functionality", and the LLM returns structured JSON. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Fields: `type:"prompt"`, `prompt` (`$ARGUMENTS` is replaced by the input JSON; if it is absent, the JSON is appended), `model` (optional), `timeout` (default 30 s), `continueOnBlock` (default false). — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Response schema: `{"ok": true|false, "reason": "...", "impossible": true|false}`. On Stop/SubagentStop with `ok:false`, "the reason is fed back to Claude as its next instruction and the turn continues, unless the response also sets `impossible: true`, in which case Claude Code allows the stop". On PreToolUse with `ok:false` the tool is denied, and by default the turn ends. `continueOnBlock:true` returns the reason to Claude instead. On PostToolUse the turn ends by default. On PermissionRequest and PermissionDenied, `ok:false` has no effect. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Agent hooks: "spawns a subagent that can read files, search code, and inspect the codebase". It "can use tools like Read, Grep, and Glob". "After up to 50 turns, the subagent returns a structured `{ "ok": true/false }` decision". The default timeout is 60 s. There is no `continueOnBlock` (it behaves as if true) and no `impossible`. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Agent hook example on Stop: `{"type":"agent","prompt":"Verify that all unit tests pass. Run the test suite and check the results. $ARGUMENTS","timeout":120}`. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Concurrency: when more than 12 prompt/agent hooks match an event, 12 run at once. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- "Agent hooks are experimental. Behavior and configuration may change in future releases. For production workflows, prefer command hooks." — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Background-model token usage is billed. The docs link "background functionality" to the costs page. — [Hooks reference](https://code.claude.com/docs/en/hooks) (link to costs.md#background-token-usage)

### Inferences
- A prompt hook only sees `$ARGUMENTS` (the hook input: `last_assistant_message`, `transcript_path` as a string). It cannot open the transcript. An agent hook can Read `transcript_path` and project files, so it is the type that can verify claims like "I ran the tests" against real logs. The 60 s default timeout is too short for running test suites; raise it.
- The `impossible` escape on prompt Stop hooks gives the judge model a way to let a non-compliant agent stop. For strict gates, prefer command hooks with deterministic checks, or agent hooks, which lack `impossible`.
- Reliability: both are LLM judgments and therefore probabilistic. Use them as a second layer on top of deterministic command checks.

### Gaps
- The docs do not state which exact model the "background" model is, its per-call price, or whether an agent hook can run Bash (the docs list "Read, Grep, and Glob" as examples, and the example prompt says "Run the test suite", which implies Bash may be available). Not confirmed.

## 4. Permissions: rule syntax, file protection, bypasses, precedence, managed settings

### Takeaway
Rules are evaluated deny → ask → allow across all scopes, and a deny anywhere cannot be overridden by an allow anywhere. Edit/Read deny rules now also cover recognized Bash file commands (cat, sed, tee, redirections). They do not cover scripts (python/node) or indirect reads, so only the sandbox gives OS-level protection. `.claude/` is a protected path: writes prompt in default/acceptEdits mode, go to the classifier in auto mode, and are allowed in bypassPermissions mode. A user-level `disableBypassPermissionsMode:"disable"` locks bypass mode out. Managed settings on Windows live at `C:\Program Files\ClaudeCode\managed-settings.json` (admin-writable) or in `HKLM\SOFTWARE\Policies\ClaudeCode`.

### Cited Findings
- "Rules are evaluated in order: deny, then ask, then allow. The first match in that order determines the outcome, and rule specificity doesn't change the order." "An allow rule can't carve an exception out of a deny rule." — [Permissions](https://code.claude.com/docs/en/permissions)
- A bare tool deny (for example `Bash`) removes the tool from Claude's context entirely. A scoped deny such as `Bash(rm *)` blocks matching calls. — [Permissions](https://code.claude.com/docs/en/permissions)
- "Permission rules are enforced by Claude Code, not by the model. Instructions in your prompt or CLAUDE.md shape what Claude tries to do, but they don't change what Claude Code allows." — [Permissions](https://code.claude.com/docs/en/permissions)
- Bash syntax: `*` matches any text including spaces. `Bash(ls *)` also matches bare `ls`. `:*` is an equivalent trailing wildcard, recognized only at the end of a pattern. Compound commands are split on `&&`, `||`, `;`, `|`, `|&`, `&` and newlines. Deny/ask rules apply if any subcommand matches, including subshells, `$(...)` and loop bodies. — [Permissions](https://code.claude.com/docs/en/permissions)
- Wrappers stripped before matching: `timeout`, `time`, `nice`, `nohup`, `stdbuf`, `command`, `builtin`, `noglob`, and bare `xargs`. Deny rules match past any leading env assignment. — [Permissions](https://code.claude.com/docs/en/permissions)
- What Bash rules don't stop: `Bash(rm *)` does not stop `/bin/rm -rf build/` or `bash -c 'rm -rf build/'`. `Bash(git push *)` does not stop `git -C . push`. "a deny or ask rule covers the invocation Claude usually produces and isn't a security boundary around the program." Use the sandbox or a PreToolUse hook. — [Permissions](https://code.claude.com/docs/en/permissions)
- Read/Edit deny scope: "Read and Edit deny rules apply to Claude's built-in file tools, to file commands Claude Code recognizes in Bash, such as `cat`, `head`, `tail`, `sed`, and `tee`, and to the targets of Bash redirections such as `> file` and `< file`. They don't apply to a command that reads files without naming them, such as `grep -r pattern .` ..., or to arbitrary subprocesses that read or write files indirectly, like a Python or Node script that opens files itself. For OS-level enforcement ... enable the sandbox." — [Permissions](https://code.claude.com/docs/en/permissions)
- Output redirects (`>`, `>>`, `2>`) and `tee` targets are checked against Edit allow/deny rules and protected paths (`tee` from v2.1.269, input redirects from v2.1.257). — [Permissions](https://code.claude.com/docs/en/permissions)
- `Write(path)`, `NotebookEdit(path)`, `Glob(path)` and `MultiEdit(path)` path rules "never match". Use `Edit(path)` for all edits and `Read(path)` for reads. A `Read` deny also blocks Edit and Write on the same path (Write from v2.1.228), but NotebookEdit is not covered, so add an `Edit` deny as well. — [Permissions](https://code.claude.com/docs/en/permissions)
- Path anchors (gitignore syntax): `//path` is absolute, `~/path` is home, `/path` is relative to the settings source (project root for project or local settings, `~/.claude/` for user settings), and `path` or `./path` is relative to cwd. "On Windows, paths are normalized to POSIX form before matching. `C:\Users\alice` becomes `/c/Users/alice`." — [Permissions](https://code.claude.com/docs/en/permissions)
- Deny rules apply if either the symlink path or its target matches. Allow rules require both to match. — [Permissions](https://code.claude.com/docs/en/permissions)
- PowerShell rules: `PowerShell(Remove-Item *)`. Aliases are canonicalized, matching is case-insensitive, and compound commands are split by AST. — [Permissions](https://code.claude.com/docs/en/permissions)
- Hooks vs rules: "PreToolUse hook decisions don't bypass permission rules ... a matching deny rule blocks the call, and a matching ask rule still prompts even when the hook returned allow." "A hook that exits with code 2 stops the tool call before permission rules are evaluated." — [Permissions](https://code.claude.com/docs/en/permissions)
- Mods caveat: without managed settings and without a Team/Enterprise `/login`, an installed mod handling `tool.check` "can approve a call that a deny rule refuses or a PreToolUse hook blocked". — [Permissions](https://code.claude.com/docs/en/permissions); [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- Modes: `default` (labeled Manual), `acceptEdits`, `plan`, `auto` (classifier), `dontAsk` (auto-denies anything that would prompt), `bypassPermissions`. — [Permissions](https://code.claude.com/docs/en/permissions)
- `permissions.disableBypassPermissionsMode` and `permissions.disableAutoMode` set to `"disable"` work "in any settings file". The docs say this "works from any scope. A user can set it in their own settings to lock themselves out of bypass mode." — [Permissions](https://code.claude.com/docs/en/permissions)
- `permissions.defaultMode` values `auto`/`bypassPermissions` don't take effect from project or local settings (since v2.1.257). — [Settings](https://code.claude.com/docs/en/settings)
- Protected paths: "Writes to a small set of paths are never auto-approved, except in bypassPermissions mode". The per-mode table: default/acceptEdits "Prompted", auto "Routed to the classifier", dontAsk "Denied", bypassPermissions "Allowed". "permissions.allow rules ... do not pre-approve protected-path writes." Protected directories include `.git`, `.claude` (with exceptions such as `.claude/worktrees/`, plan files, and auto-memory markdown), `.vscode`, `.husky` and others. Protected files include `.mcp.json`, `.claude.json`, `.gitconfig`, shell rc files, and `.pre-commit-config.yaml`. — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- The protected-path prompt can offer a session-scoped option: "Yes, and allow Claude to edit files in this project's .claude folder for this session." — [Permission modes](https://code.claude.com/docs/en/permission-modes) (as summarized by fetch)
- Actions no mode auto-approves: explicit ask rules, `AskUserQuestion`, `rm`/`rmdir` critical-path removals, and others. — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- Settings precedence: 1 Managed, 2 Command line (`--settings`), 3 Project local (`.claude/settings.local.json`), 4 Shared project (`.claude/settings.json`), 5 User (`~/.claude/settings.json`). List keys such as `permissions.allow` merge across scopes. On Windows, `~/.claude` means `%USERPROFILE%\.claude`. — [Settings](https://code.claude.com/docs/en/settings)
- "If a tool is denied at any level, no other level can allow it ... a user-level deny blocks a project-level allow." — [Permissions](https://code.claude.com/docs/en/permissions)
- Settings are hot-reloaded: "Claude Code watches your settings files and reloads them when they change, so it applies most edits to the running session without a restart, including edits to permissions, hooks". It runs a ConfigChange hook for each settings-file change it detects. — [Settings](https://code.claude.com/docs/en/settings)
- Project `permissions.allow` and `additionalDirectories` wait for workspace trust. `deny`/`ask` rules apply immediately. Hooks in settings files also wait for trust in interactive sessions, but in `-p`/SDK sessions they run without the dialog. — [Permissions](https://code.claude.com/docs/en/permissions); [Hooks reference](https://code.claude.com/docs/en/hooks)
- `disableAllHooks` in user settings alone isn't enough, because "the repository's project settings take precedence over yours and can set it back to false". — [Permissions](https://code.claude.com/docs/en/permissions)
- Managed settings on Windows: the file is at `C:\Program Files\ClaudeCode\managed-settings.json` (plus `managed-settings.d/` and `managed-mcp.json` in the same directory). "Claude Code doesn't read the legacy Windows path `C:\ProgramData\ClaudeCode\managed-settings.json`." The registry location is `HKLM\SOFTWARE\Policies\ClaudeCode`, value `Settings` (REG_SZ JSON). There is also an HKCU fallback at `HKCU\SOFTWARE\Policies\ClaudeCode`, which is user-writable and used only when no admin document is present. — [Managed settings](https://code.claude.com/docs/en/managed-settings)
- "a developer who is an administrator on the machine can edit the managed source itself." — [Managed settings](https://code.claude.com/docs/en/managed-settings)
- Managed-only keys: `allowManagedHooksOnly` ("When true, restricts which hooks run") and `allowManagedPermissionRulesOnly` ("Makes managed settings the only settings source of permission rules"). `allowManagedHooksOnly` and `permissions.disableBypassPermissionsMode` are "Locks" that apply the strictest value any source sets. — [Managed settings](https://code.claude.com/docs/en/managed-settings)
- With `allowManagedHooksOnly`, user, project, local and plugin hooks are blocked, except force-enabled plugins, and `/hooks` shows "Only hooks from managed settings run here". — [Hooks reference](https://code.claude.com/docs/en/hooks); [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- `disableAllHooks:true` "can't disable managed hooks from outside managed settings." — [Hooks reference](https://code.claude.com/docs/en/hooks)
- An unparseable managed settings file makes Claude Code refuse to start. — [Managed settings](https://code.claude.com/docs/en/managed-settings)

### Inferences
- **Can the agent edit `.claude/settings.json` or its hook scripts?** In default/acceptEdits mode it prompts, and the user can approve, possibly for the whole session. In auto mode the classifier decides. In bypassPermissions mode it is allowed silently. Bash writes through `python`/`node` are not caught by Edit deny rules. Concrete layering:
  1. Put the hooks and deny rules in `C:\Program Files\ClaudeCode\managed-settings.json`. This path is not writable without admin rights, and the user here runs as a normal user, which needs confirming. Set `allowManagedHooksOnly:true` so project and user files cannot add or disable hooks, and set `permissions.disableBypassPermissionsMode:"disable"`.
  2. Add `Edit` deny rules for test files, measurement scripts and hook scripts, for example `Edit(//c/Program Files/ClaudeCode/**)` and `Edit(/tests/**)`. Also add `Read`-independent `Edit` denies, because NotebookEdit is not covered by Read denies.
  3. Add a PreToolUse command hook on `Bash|PowerShell` that refuses commands mentioning protected paths, `python -c`, or `node -e` writes. Use exit 2 with `onFailure:"block"`.
  4. Add a ConfigChange hook that blocks `project_settings`/`local_settings` changes (policy changes cannot be blocked anyway).
  5. Add a FileChanged watcher for alerts.
  6. For hard guarantees, enable the sandbox (OS-level filesystem write restrictions), which the docs repeatedly name as the only complete control.
- Hook scripts stored inside the repo (`.claude/hooks/`) are inside the protected `.claude` directory, but bypass mode or an approved session-wide `.claude` edit defeats that. Keeping the scripts outside the repo, in the managed directory, is safer.

### Gaps
- I did not fetch the sandboxing page itself, so the exact filesystem write-deny config for the sandbox (`sandbox.filesystem...`) and its Windows support are not confirmed here. Sandbox support on native Windows is uncertain and needs checking.
- The full `allowManagedHooksOnly` effect list (settings-reference#what-runs-under-allowmanagedhooksonly) was not fetched.

## 5. Hook configuration on Windows, and testing

### Takeaway
On Windows, use exec form (`command` + `args`) to avoid shell quoting, for example `"command":"node","args":["${CLAUDE_PROJECT_DIR}/.claude/hooks/x.js"]`. Without Git Bash, shell-form hooks run in PowerShell, and failed PreToolUse hooks block. Test by piping JSON into the script, and check `/hooks` and `claude --debug` (log in `~/.claude/debug/<session-id>.txt`).

### Cited Findings
- Exec form: "When `args` is present, `command` is resolved as an executable and spawned directly with args as the argument vector, with no shell involved". Shell form (command alone) "runs through `sh -c`, Git Bash, or PowerShell. Prefer exec form when a path placeholder is used." Example: `{"type":"command","command":"node","args":["${CLAUDE_PLUGIN_ROOT}/scripts/format.js","--fix"]}`. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- `shell` field: `"bash"` or `"powershell"`. It defaults to bash, or to powershell on Windows when Git Bash isn't installed, and it is ignored when `args` is set. Claude Code auto-detects `pwsh.exe` and falls back to `powershell.exe`. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- In PowerShell shell form, write `${CLAUDE_PROJECT_DIR}` or `$env:CLAUDE_PROJECT_DIR`, never bare `$CLAUDE_PROJECT_DIR`, which PowerShell resolves to `$null`. Example: `{"type":"command","shell":"powershell","command":"& \"$env:CLAUDE_PROJECT_DIR\\.claude\\hooks\\check.ps1\""}`. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- The official PowerShell exec-form pattern: `"command":"powershell.exe","args":["-NoProfile","-ExecutionPolicy","Bypass","-File","${CLAUDE_PROJECT_DIR}/.claude/hooks/block-opus-46.ps1"]`, with the script reading `[Console]::In.ReadToEnd() | ConvertFrom-Json`, writing to `[Console]::Error` and calling `exit 2`. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Windows without Git Bash: the error text is "blocking because Git Bash wasn't found, so only exit code 0 or 2 counts as this hook's verdict". Without Git Bash, any exit code other than 0 or 2 counts as a failure. The fixes include installing Git for Windows, setting `CLAUDE_CODE_GIT_BASH_PATH`, or `onFailure`. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- `$CLAUDE_PROJECT_DIR` is the project root where the session started. It stays the same even after `/cd`. — [Hooks reference](https://code.claude.com/docs/en/hooks); [Permissions](https://code.claude.com/docs/en/permissions)
- Timeouts: 600 s for command/http/mcp_tool, 30 s for prompt, 60 s for agent. Command/http/mcp_tool drop to 30 s on UserPromptSubmit, PreModelSwitch and PostModelSwitch. SessionEnd has a 1.5 s budget, raisable to 60 s. Matching hooks run in parallel. An identical handler defined in several settings files runs once. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Config locations: `~/.claude/settings.json`, `.claude/settings.json`, `.claude/settings.local.json`, managed policy, plugin `hooks/hooks.json`, skill frontmatter (active for the rest of the session once the skill is invoked), and subagent frontmatter (only while that subagent runs; a `Stop` there becomes `SubagentStop`). — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Testing: `/hooks` opens a read-only browser showing each hook's source and command. Manual test: `echo '{"tool_name":"Bash","tool_input":{"command":"ls"}}' | ./my-hook.sh; echo $?`. `claude --debug` writes to `~/.claude/debug/<session-id>.txt` (it does not print to the terminal), or use `--debug-file <path>`. `CLAUDE_CODE_DEBUG_LOG_LEVEL=verbose` adds matcher detail. Ctrl+O opens the transcript view to show hook outcomes. — [Hooks reference](https://code.claude.com/docs/en/hooks); [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- Debug log lines (v2.1.296+): `Hooks: PostToolUse:Write [.claude/hooks/log-write.sh] finished with status 0 (31ms)`. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- If `/hooks` shows nothing after an edit: "the file watcher may have missed the change: restart your session". JSON must be strict (no trailing commas or comments). — [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- `/config` and possibly `/hooks` are terminal UI. "The desktop app don't open it [/config]". — [Settings](https://code.claude.com/docs/en/settings). A GitHub report notes `/hooks` is not available in the Desktop app UI — [claudeissues mirror #81788](https://claudeissues.com/issue/81788-notification-hooks-permission-prompt-idle-prompt-never-fire-in-desktop-app)

### Inferences
- For this Windows project, use node scripts in exec form, which avoids both Git Bash profile noise and PowerShell 5.1 quirks. Exit 0 with JSON on stdout, or exit 2 with the reason on stderr. Add `onFailure:"block"` on PreToolUse guard hooks.

### Gaps
- None critical. The exact name of the `CLAUDE_CODE_GIT_BASH_PATH` fix bullets was truncated.

## 6. Known bugs and limitations (GitHub issues)

### Takeaway
There are many 2026 reports of Stop hooks firing intermittently, settings.json Stop hooks not dispatching while plugin ones do, Desktop app and VS Code differences, and deny rules not enforced (including the agent editing settings files). Most are closed, but some are still open. Treat hooks and deny rules as strong but not infallible, and verify them in the exact surface used (here, the Desktop app).
